# 🚀 EmailClaw 第三阶段工作总结 (飞书交互闭环与真实邮件操作)

本阶段在第二阶段已经完成的 **Agent 分析层基础框架** 之上，重点推进 EmailClaw 的用户交互闭环：将后端分析结果推送到飞书机器人卡片，并让用户能够通过飞书按钮反向触发后端操作数据库和真实邮箱。

本阶段的核心目标是让系统从“能分析邮件”进一步升级为“能在飞书中展示邮件，并支持交互式处理邮件”。

---

## 🛠 已完成的核心任务

### 1. 打通后端到飞书 bot 的通知链路

本阶段新增了主后端与飞书 bot 之间的 HTTP 通道。

当前邮件处理主流程为：

```text
IMAP 监听
  -> 抓取新邮件
  -> mailparser 解析邮件
  -> 保存 Email 到 PostgreSQL
  -> Agent 分析分类、重要性、摘要
  -> 保存分析结果
  -> 后端调用 FeishuService
  -> 推送数据到飞书 bot
  -> 飞书 bot 构建并发送交互式卡片
```

其中主后端通过 `FEISHU_BOT_URL` 调用飞书 bot 的：

```http
POST /api/notify-email
```

飞书 bot 接收到后端推送的数据后，使用卡片构建器生成飞书交互式卡片，并通过飞书 OpenAPI 发送给指定用户。

### 2. 飞书邮件卡片展示能力

本阶段实现了邮件通知卡片的完整展示结构。

卡片中包含：

- 邮件主题。
- 发件人、收件人。
- 收到时间。
- AI 分类结果。
- 分类置信度。
- 重要性评分。
- 邮件摘要。
- 分类理由。
- 当前状态：未读、已读、已归档、已删除。

卡片支持的操作按钮包括：

- 标为已读。
- 标为重点。
- 归档。
- 删除。
- 分类正确。
- 分类错误。
- 查看详情。
- 重新分析。

不同邮件分类会使用不同卡片 header 颜色，方便用户快速区分邮件类型。

### 3. 飞书按钮回调到后端

本阶段新增飞书 webhook 路由：

```http
POST /api/feishu/webhook
```

飞书 bot 监听 `card.action.trigger` 事件，解析用户点击的按钮 action 和 emailId，然后转发给主后端。

后端统一通过 `FeishuService.handleCallback()` 分发处理不同 action：

- `mark_read`
- `mark_important`
- `archive`
- `delete`
- `feedback_correct`
- `feedback_wrong`
- `view_detail`
- `reanalyze`

这一步完成了飞书端到后端业务逻辑的反向通道。

### 4. 真实邮箱操作与数据库状态同步

本阶段将飞书按钮操作接入真实 IMAP 邮箱和 PostgreSQL 数据库。

当前支持：

- **标为已读**：IMAP 添加 `\Seen`，数据库更新 `Email.isRead = true`。
- **标为重点**：IMAP 添加 `\Flagged`，数据库更新 `Email.importance = 10`。
- **归档邮件**：IMAP 移动到配置的归档目录，数据库更新 `Email.isArchived = true`。
- **删除邮件**：IMAP 添加 `\Deleted` 并执行 `expunge`，数据库更新 `Email.isDeleted = true`。
- **分类反馈**：写入或更新 `Classification.feedback`。
- **分类错误纠正**：记录用户选择的正确分类，并同步更新 `Email.category`。

同时，IMAP 操作已经从“只触发不确认”升级为“等待回调确认”：

```text
IMAP 操作成功
  -> 更新数据库
  -> 返回成功
  -> 飞书卡片刷新状态

IMAP 操作失败
  -> 不返回假成功
  -> 飞书端展示失败提示
```

这避免了“邮箱操作失败但用户看到已完成”的状态不一致问题。

### 5. 详情卡片与卡片状态刷新

本阶段补全了飞书端的后续交互体验。

点击“查看详情”后：

```text
飞书按钮
  -> bot 转发 view_detail
  -> 后端返回邮件详情
  -> bot 构建详情卡片
  -> 飞书展示正文预览
```

详情卡片中包含：

- 邮件主题。
- 发件人、收件人。
- 收到时间。
- 分类和重要性。
- 邮件摘要。
- 正文预览。

对于已读、重点、归档、删除、反馈和重新分析等操作，后端会返回最新邮件状态，bot 端会重新构建卡片并刷新原卡片，而不再只是弹出 toast。

### 6. 重新分析逻辑优化

第二阶段中，重新分析还没有进入飞书交互流程。

本阶段将 `reanalyze` 实现为：

```text
查询当前 Email
  -> 重新构造 SimpleEmail
  -> 调用 AgentService.analyzeEmailDraft()
  -> 更新当前邮件的分类、重要性、摘要
  -> 更新 Classification 和 AgentLog
  -> 返回最新邮件状态
  -> 刷新当前飞书卡片
```

与初版思路相比，当前实现不会复用 `processEmail()`，因此不会重复推送一张新的飞书卡片。

### 7. 数据库字段补充与迁移

为了支持卡片状态和摘要持久化，本阶段为 `Email` 模型补充了字段：

- `summary`: 保存邮件摘要。

并新增 Prisma migration：

## ⚠️ 重要说明

### 1. OpenClaw 不是必需项

当前系统默认可以使用本地规则 Agent 运行。

```text
OPENCLAW_ENABLED=false
```

这种模式不需要外部大模型 API，也不需要 OpenClaw 本地运行时。

如果开启：

```text
OPENCLAW_ENABLED=true
```

后端会尝试调用 OpenClaw，由 OpenClaw 进一步调用其配置的大模型。OpenClaw 调用失败时，系统会回退到本地规则 Agent。

### 2. 本阶段代码完成的是 MVP 闭环

当前代码已经具备演示和联调所需的核心功能，但还没有完成生产级部署与稳定性打磨。

后续联调中仍可能出现：

- 不同邮箱服务商对 IMAP 归档目录命名不同。
- 某些邮箱不支持自定义 `CLAWED` flag。
- 飞书开放平台权限或事件字段与预期略有差异。
- 本地 PostgreSQL 与 Prisma 版本需要进一步统一。
- OpenClaw 的模型输出质量需要 Prompt 调优。

## 🐛 修复：飞书交互卡片刷新链路根治

### 现象
- "查看详情" 点击后无反应（详情卡片渲染失败）。
- "分类正确 / 分类错误" 后卡片状态不刷新，只弹出默认 toast。
- "标为已读 / 重点 / 归档 / 删除" 后卡片状态也不会变。

### 根因
原 `feishuRoutes.ts` 为了规避飞书 3 秒回调超时，把 webhook 处理改成"立即返回空 `{}` + 后台异步执行"。这让 bot 端拿到的 `result.detail` 和 `result.email` 永远是 `undefined`，所有依赖回包刷新卡片的逻辑全部失效。

### 修复方案（采取根治路径而非 hack）
1. **后端恢复同步语义**：`src/backend/api/routes/feishuRoutes.ts` 改回 `await feishuService.handleCallback(...)` 后返回完整结果。
2. **bot 端"先 toast、再异步 updateCard"**：`email_claw_bot/src/handlers/cardHandler.js` 收到按钮事件后毫秒级返回 `{toast: '处理中...'}` 让飞书停止倒计时；在后台 `await` 后端、再通过 `feishuClient.updateCard(messageId, ...)` 主动 patch 原卡片刷新状态。
3. **view_detail 顺手优化为新卡片**：详情用 `sendCard` 新发一张，保留原邮件卡片的所有按钮，UX 更合理。
4. **失败可见化**：后端或刷新链路任意环节失败时，bot 会通过 `sendText` 给用户发明确的失败提示，不再静默吞错。

这样既不触发飞书 3 秒红色错误，又能保证所有按钮交互的卡片刷新都正确生效。

## 🔐 1. 多用户与认证体系（FR-1 基础）

### 原状
- `User` 模型早已设计，但代码完全没消费——IMAP 凭据全部读自 `.env`，是单用户硬编码模式。
- 没有注册 / 登录 API，没有密码哈希，没有 IMAP 凭据加密。

### 本次新增
- **密码哈希**：`bcryptjs`，12 轮 salt。
- **JWT 鉴权**：`jsonwebtoken` 签发 7 天有效期 access token，中间件 `requireAuth` 校验 `Authorization: Bearer <token>`。
- **IMAP 凭据加密入库**：自研 `src/backend/utils/crypto.ts`，使用 AES-256-GCM；密钥取自 `ENCRYPTION_KEY` 环境变量，经 sha-256 派生为 32 字节 key。
- **认证路由**：
  - `POST /api/auth/register   {email, password}`
  - `POST /api/auth/login      {email, password}` → `{token, user}`
- **用户自管理路由**（全部走 JWT）：
  - `GET    /api/users/me`
  - `PATCH  /api/users/me/preferences   {importanceThreshold, pushAllEmails}`
  - `PATCH  /api/users/me/feishu        {feishuUserId}`
  - `POST   /api/users/me/mailbox       {imapHost, imapUser, imapPassword}` — 自动加密入库并即时启动该用户 IMAP 连接
  - `DELETE /api/users/me/mailbox` — 解绑邮箱、断开 IMAP

### 多用户 IMAP 架构重构

将原本 `EmailService` 单例的全局 IMAP 连接拆分为：

- **`src/backend/services/userMailbox.ts`**：单个用户的 IMAP 长连接与邮件操作（read / flag / archive / delete），所有日志带 `[user=...]` 前缀。
- **`src/backend/services/imapManager.ts`**：多用户 IMAP 连接注册表，提供 `startForAllBoundUsers / startForUser / stopForUser / getMailboxForEmail` 接口。
- **`src/backend/services/emailService.ts`**：重构为 facade，对外 API 不变，内部全部走 `imapManager`，并在每个写操作前强制 ownership 校验。

### 引导用户机制
新建 `src/backend/services/bootstrap.ts`：服务启动时，如果 `.env` 配置了 `IMAP_USER` 且 `BOOTSTRAP_PASSWORD` 不为空，会自动注册一个引导用户并加密绑定该邮箱。如果数据库里已存在该 email 的用户，则只补齐 / 更新 IMAP 凭据。这保证了既有的单用户 `.env` 配置在多用户化后仍能直接跑起来。

## 🛡 2. 防御性鉴权三层防线

按用户要求"对不同邮箱的鉴权做可能的防御性"专门强化：

| 层 | 位置 | 内容 |
|---|---|---|
| **HTTP** | `requireAuth` / `requireBotSecret` 中间件 | 所有用户 API 强制 JWT；飞书 webhook 必须带 `X-Bot-Secret` |
| **业务** | `feishuRoutes.ts` | 先把 `openId → userId`；未绑定飞书的请求直接 403 |
| **数据** | `databaseService.assertEmailOwnership(emailId, userId)` | 每次写操作前校验 emailId 归属；规则 CRUD 用 `updateMany / deleteMany where userId` 防止越权修改他人规则 |

### 端到端越权验证
启动后实测：
- 攻击者用自己的 JWT 读受害者 emailId → `{"error":"无权操作此邮件"}`
- 攻击者 `/api/emails` 列表 → `{"items":[],"total":0}`
- 未带 `X-Bot-Secret` 调 webhook → `{"error":"bot 共享密钥校验失败"}`

## 📏 3. 规则引擎（FR-5）

### 数据模型
复用既有 `Rule` 表，约定 JSON 结构：

```json
{
  "conditions": [
    { "field": "from|to|subject|body",
      "operator": "contains|equals|startsWith|endsWith|regex",
      "value": "...", "caseSensitive": false }
  ],
  "actions": {
    "category": "work|personal|shopping|marketing|spam|other",
    "importance": 8,
    "summary": "可选自定义摘要",
    "sideEffects": ["mark_read", "archive", "delete"]
  }
}
```

多个 conditions 之间 AND 关系。按 `priority` 降序匹配，首个命中即返回。

### 执行策略
`src/backend/services/ruleEngine.ts` 在 Agent 之前运行，**命中即跳过 Agent**：

- 命中后还会执行 `sideEffects`（mark_read / archive / delete）走 IMAP 真实操作

### CRUD API
`src/backend/api/routes/ruleRoutes.ts` 提供完整的 `GET/POST/PATCH/DELETE`，全部走 JWT + userId 隔离。
